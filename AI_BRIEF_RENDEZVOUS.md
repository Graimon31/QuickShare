# Запрос: публичная точка обмена на 200 байт, без своей инфраструктуры, работающая из России

## Задача в одном абзаце

Нужно доставить **одно сообщение размером ~200 байт, один раз за сессию**, от мобильного устройства к десктопу, когда десктоп недостижим для входящих соединений. Своего сервера нет и не будет — принципиальное требование продукта. Нужна уже существующая публичная инфраструктура, куда мобильное устройство кладёт данные, а десктоп забирает их **исходящим** запросом. После этого обмена данные идут напрямую P2P и посредник больше не участвует.

Вопрос: **какие конкретно публичные точки обмена реально работают из российских сетей в 2026 году, не требуют регистрации и не требуют разворачивать сервер?**

---

## Контекст (кратко)

Приложение QuickShare: Flutter/Dart, передача файлов P2P между macOS/iOS/Android/Windows/Linux. LAN и Bluetooth работают. Проблема только в интернет-режиме через WebRTC DataChannel.

Схема обмена: десктоп показывает QR-код, мобильное устройство его сканирует. **Обратного визуального канала нет** — десктопные версии приложения камеру не используют, только показывают QR. Это продуктовое требование, двусторонний QR отвергнут.

Поэтому SDP Offer доезжает до телефона в QR-коде, а SDP Answer доставить обратно нечем.

## Что уже измерено на реальной сети (не предположения)

Замеры сделаны с десктопа в российской домашней сети, VPN выключен.

**Тип NAT — отображение (RFC 4787 mapping):**
```
один UDP-сокет, локальный порт 64990:
  stun.sipnet.ru       -> 195.170.199.39:42242
  stun.fitauto.ru      -> 195.170.199.39:42242
  stun.ru-brides.com   -> 195.170.199.39:42242
  stun.cloudflare.com  -> 195.170.199.39:42242
```
Внешний порт одинаков для всех адресатов → **Endpoint-Independent Mapping (cone NAT)**. UDP hole punching работает, симметричного NAT нет.

**Тип NAT — фильтрация (RFC 5780):**
```
Тест 2 (change-ip + change-port через stun.fitauto.ru): ответа нет
Тест 3 (change-port):                                   ответа нет
```
→ **Address-and-Port-Dependent Filtering (port-restricted cone)**. Незнакомый хост не может прислать пакет на внешний порт.

**Прочее:**
- UPnP/IGD: SSDP M-SEARCH с привязкой к физическому интерфейсу — ответа нет. Проброс порта недоступен.
- IPv6: глобальных адресов нет, связности нет.
- `stun.l.google.com:19302` — **таймаут** из реальной российской сети (через VPN отвечал за 459 мс). Живые: `stun.cloudflare.com`, `stun.sipnet.ru`, `stun.fitauto.ru`, `stun.ru-brides.com`.
- TCP-коннект есть: `openrelay.metered.ca:80`, `openrelay.metered.ca:443`, `turn.cloudflare.com:443`. Не резолвится: `relay.expressturn.com`.
- У пользователей часто активен VPN, перехватывающий маршрут по умолчанию.

## Вывод, который мы сделали

Обратный канал перекрыт с обеих сторон: визуального нет по продуктовому решению, сетевого нет из-за фильтрации NAT. Значит нужна третья точка. Но нужна она **только на 200 байт и только один раз** — файл пойдёт напрямую, так как hole punching работает.

Если этот вывод неверен и есть способ доставить 200 байт на port-restricted cone NAT без третьей стороны — это самый ценный ответ, напишите его первым.

## Вопросы

1. **Какие публичные точки обмена без регистрации реально доступны из РФ сейчас?** Интересуют замеры/опыт, а не общие списки. Кандидаты, которые мы рассматриваем:
   - публичные MQTT-брокеры (`test.mosquitto.org`, `broker.hivemq.com`, `broker.emqx.io`) — TLS на 8883
   - Nostr-релеи по WSS:443
   - WSS-трекеры WebTorrent (`tracker.openwebtorrent.com` и аналоги)
   - **BitTorrent Mainline DHT, BEP 44** — put/get произвольных данных до 1000 байт в DHT. Формально это вообще не сервер: данные лежат в распределённой сети пиров. Насколько это живо и достижимо из РФ, какова латентность put→get, доступны ли bootstrap-узлы, и есть ли пригодная реализация для Dart/Flutter?
   - IPFS pubsub
   - публичные pastebin-подобные API без ключа

2. **Что из этого переживает DPI и блокировки в РФ?** Приоритет — TLS на 443, чтобы трафик был неотличим от HTTPS. Что реально не режется?

3. **Латентность и надёжность.** Пользователь стоит с телефоном у экрана. Приемлемая задержка на доставку 200 байт — до 3–5 секунд. Что из списка укладывается, а что даёт десятки секунд?

5. **Есть ли механизм, который мы упускаем?** Например: способы заставить port-restricted NAT принять пакет от неизвестного хоста; использование самого STUN-сервера как точки встречи; birthday-атака / port prediction применительно к cone NAT с EIM; что-то ещё.
